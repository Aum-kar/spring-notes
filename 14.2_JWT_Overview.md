# JWT Authentication Overview

In JWT authentication:
- User logs in using username and password.
- Server verifies password using BCrypt.
- If valid:Server generates:
    - Access token (short-lived)
    - Refresh token (longer-lived, optional but common)
- Tokens are sent to client, client stores them.
- For every request, Client sends: `Authorization: Bearer <access_token>`
- Server does not store session data.


## Access Token

- Used to access protected endpoints.
- Short expiration time (e.g., 10–15 minutes).
- Contains:
    - Subject (username)
    - Roles
    - Issued at
    - Expiration time
- Verified on every request.


## Refresh Token
 
- Used to generate new access tokens.
- Longer expiration time.
- Sent to a refresh endpoint when access token expires.
- Should be stored securely.


## JWT Structure

JWT has three parts: `base64Url(header).base64Url(payload).base64Url(signature)`


### Header

Contains metadata.  
Example:
```json
{
    "alg": "HS256", 
    "typ": "JWT" 
}
```


### Payload

- Contains claims.
- Payload is readable.
- Do not store sensitive data like Password, Secrets, Private data, etc.

Example:
```json
{ 
    "sub": "username", 
    "roles": ["ADMIN"], 
    "iat": 1234567890, 
    "exp": 1234569999 
}
```


### Signature

- Created using:  
 `HMACSHA256( base64Url(header) + "." + base64Url(payload), secret_key )`  
- Ensures token integrity. If payload is modified, verification fails.

## Security Properties

- JWT is signed, not encrypted.
- Anyone can decode header and payload.
- Only server can verify signature (if secret is secure).
-If token is altered, verification fails.
- Must be used over HTTPS.
- If token is stolen, attacker can use it until expiration.


## Benefits of JWT

1. Client does not send credentials on every request.
2. Server does not store session data.
3. Backend does not need to check password on every request.
4. Scales well in distributed systems.5. Stateless architecture.


> JWT reduces DB dependency, but does not always eliminate it completely.
