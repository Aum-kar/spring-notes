# Spring Security – Authentication and Authorization Summary

## This summary covers:

* BCrypt usage
* SecurityFilterChain configuration
* In-memory and database authentication
* Method-level authorization
* Core Spring Security interfaces
* Authentication flow


## 1. What Spring Security Does

* Spring Security adds a security filter chain before your controllers.
* Every request passes through this filter chain.
* It performs:

  * Authentication (Who are you?)
  * Authorization (Are you allowed to access this resource?)

Request Flow (Simplified)

* Client sends HTTP request.
* Spring Security filter chain intercepts it.
* Authorization header is inspected.
* Username is extracted.
* `UserDetailsService.loadUserByUsername()` is called.
* User data is fetched (in-memory or database).
* Password is verified using `PasswordEncoder.matches()`.
* If authentication succeeds:

  * Authentication object is created.
  * Stored in SecurityContext.
* Authorization rules are checked.
* If allowed → Controller method executes.
* If not:

  * 401 → Not authenticated
  * 403 → Authenticated but not authorized

## 2. BCrypt Password Encoding

BCrypt is used to securely hash passwords.

Important points:

* Passwords must never be stored as plain text.
* BCrypt automatically adds salt.
* It is designed specifically for password hashing.
* It is adaptive (work factor can be increased).

PasswordEncoder Bean:

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

During Registration:

* Raw password → passwordEncoder.encode(rawPassword)
* Store encoded password in database.

During Login:

* Spring automatically calls:
  passwordEncoder.matches(rawPassword, storedEncodedPassword)

If matches → authentication succeeds.

## 3. Configuring SecurityFilterChain

SecurityFilterChain defines how authentication and authorization work.

Basic Configuration Example:

```java
@Configuration
@EnableWebSecurity
class SecurityConfiguration {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {

        http
            - formLogin(form -> form.disable())
            - csrf(csrf -> csrf.disable())
            - authorizeHttpRequests(authorize -> authorize
                - requestMatchers("/api/public/**").permitAll()
                - anyRequest().authenticated()
            )
            - httpBasic(withDefaults())
            - sessionManagement(session ->
                session.sessionCreationPolicy(SessionCreationPolicy.STATELESS)
            );

        return http.build();
    }
}
```

Explanation:

* formLogin().disable()

  * Disables default login page.
* csrf().disable()

  * Often disabled for stateless APIs.
* requestMatchers()

  * Defines URL-based authorization.
* httpBasic()

  * Enables HTTP Basic authentication.
* STATELESS

  * No session stored on server.
  * Each request must include credentials.

## 4. In-Memory Users

Used for simple applications or testing.

```java
@Bean
public UserDetailsService userDetailsService(PasswordEncoder encoder) {

    UserDetails user = User.builder()
        - username("user")
        - password(encoder.encode("pass123"))
        - roles("USER")
        - build();

    UserDetails admin = User.builder()
        - username("admin")
        - password(encoder.encode("admin123"))
        - roles("ADMIN")
        - build();

    return new InMemoryUserDetailsManager(user, admin);
}
```

Characteristics:

* No database required.
* Users exist only in memory.
* Data resets when application restarts.

## 5. Database-Based Users

Steps:

1. Create AppUser entity.
2. Create AppUserRepository.
3. Implement UserDetailsService.

Example:

```java
@Service
public class AppUserService implements UserDetailsService {

    private final AppUserRepository userRepository;

    public AppUserService(AppUserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @Override
    public UserDetails loadUserByUsername(String username) {

        AppUser user = userRepository.findByUsername(username)
            - orElseThrow(() -> new UsernameNotFoundException(username));

        return User.builder()
            - username(user.getUsername())
            - password(user.getPassword())
            - roles(user.getRole().name())
            - build();
    }
}
```

Concept:

* Fetch entity from database.
* Convert entity → Spring Security User (UserDetails).
* Spring handles authentication using this object.

## 6. Method-Level Security with @PreAuthorize

Enable method security:

```java
@EnableMethodSecurity
```

Example:

```java
@PreAuthorize("hasRole('ADMIN')")
@GetMapping("/members/admin")
public String adminEndpoint() {
    return "Admin only";
}
```

Other examples:

* hasRole('ADMIN')
* hasAnyRole('USER','ADMIN')
* hasAuthority('ROLE_ADMIN')
* hasRole('ADMIN') and hasRole('USER')

Behavior:

* Expression evaluated before method execution.
* If false → 403 returned.
* Requires authenticated user.

Difference from URL-based security:

* URL-based → Defined in SecurityFilterChain.
* Method-level → Defined directly on methods.
* Method-level is more fine-grained.

## 7. User vs UserDetails vs UserDetailsService vs UserDetailsManager

User (org.springframework.security.core.userdetails.User)

* Built-in implementation of UserDetails.
* Represents authenticated user inside Spring Security.
* Not your database entity.

UserDetails

* Interface used by Spring Security.
* Represents user information required for authentication.
* Contains:

  * username
  * password
  * authorities
  * account status flags

UserDetailsService

* Interface with one method:
  loadUserByUsername(String username)
* Spring calls it during authentication.
* You implement it to fetch users from database.

UserDetailsManager

* Extends UserDetailsService.
* Adds user management methods:

  * createUser()
  * updateUser()
  * deleteUser()
* InMemoryUserDetailsManager is an implementation.
* Often used for in-memory authentication.

Relationship Summary:

* Your Entity → Converted to UserDetails.
* UserDetailsService → Loads user.
* User → Concrete implementation of UserDetails.
* UserDetailsManager → Advanced service for managing users.

## 8. HTTP Status Codes in Security

* 401 Unauthorized

  * User is not authenticated.
  * Missing or invalid credentials.

* 403 Forbidden

  * User is authenticated.
  * Does not have required authority.

---

## 9. Stateless vs Stateful Authentication

Stateful:

* Uses session.
* Server stores authentication.
* Browser sends JSESSIONID.

Stateless:

* No session stored.
* Each request must send credentials.
* Common for REST APIs.

Configuration:

```java
.sessionManagement(session ->
    session.sessionCreationPolicy(SessionCreationPolicy.STATELESS)
)
```
